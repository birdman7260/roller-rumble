# An event's race distance is chosen when the event is created, and a walk-up event can never change it

**Status:** accepted — resolves [issue #38](https://github.com/birdman7260/roller-rumble/issues/38) on the [walk-up event map (#30)](https://github.com/birdman7260/roller-rumble/issues/30). Builds on [ADR 0018](0018-event-kind-and-derived-capabilities.md) (`event kind`, `event capability`), [ADR 0019](0019-host-assigned-lane-swap.md) (the `lane swap` window), [ADR 0021](0021-admin-tabs-declare-the-capability-they-need.md) (`requires`, no trace) and [ADR 0022](0022-top-racers-board-ranks-one-run-per-racer.md) (the board's distance filter). **Narrows ADR 0018** on where a value that varies within a kind lives — contradicting it as written, see Consequences — and **closes ADR 0022's open consequence** that a mid-event distance change empties the board.

The `top racers board` ranks fastest time over one distance, so it means something only if every run it ranks was raced to the same line. Nothing guarantees that today. The distance is one global setting, `AdminSettings.targetDistanceMeters` (`packages/shared/src/types.ts:618`, default 250 m at `constants.ts:4`), changed from the Race Desk's `Race Distance` panel (`race-tab.tsx:114`) in two taps with no confirmation. Each race copies it when created (`app.ts:2345` queued, `:2678` tournament), so history stays interpretable — but under ADR 0022's rule, a change after ten runs empties the board, because every recorded run then fails the match.

We decided the **`race distance`** belongs to the `Event`, not to the app. Every event, of every kind, carries one, chosen in the create-event form, and every race copies it from the active event when the race is created. What differs by kind is whether it can move afterwards: a `standard` event may adjust it in place, and a `walk-up event` never can. That is one new `event capability`, **`hasAdjustableRaceDistance`** — true for `standard`, false for `walk-up` — which gates the Event tab's distance editor and which the server checks before accepting a change.

The load-bearing consequence: **no walk-up event can hold runs at two distances.** The "locked walk-up distance" ADR 0022 filters on is simply the event's race distance, and a distance change cannot empty the board because a walk-up event has no distance change.

## Considered Options

**Whether a walk-up event's distance can change**

- **Fixed at creation (chosen).** Picked alongside the kind in the create-event form and immutable afterwards, exactly like `kind` (ADR 0018). The only option under which two distances in one walk-up event are unrepresentable, so the board's comparability is a property of the data rather than of the operator. Its cost is that every correction — even one at 5:45pm before anyone has ridden — is a new event.
- **Editable, with a confirm naming the cost (rejected).** Keeps a mid-evening fix ("people are gassing out") inside one event: the board ranks only runs at the current distance and never rewrites a run, so changing back restores it. Its protection is an operator reading a confirm, where fixed-at-creation needs nobody to read anything.
- **Locked once a run qualifies (rejected).** Editable through setup and test rides, frozen at the first ranked run. The same guarantee with a harder rule to state — editable until something has happened — and the same new-event escape hatch from the first rider on.
- **Editable with no confirm (rejected).** Today's behaviour. The board stays correct, since it filters, but empties with no explanation, which is the failure the ticket exists to prevent.

**Where the distance lives**

- **On the event, for every kind (chosen).** One home: races always copy the active event's distance, and no event runs at a value left behind by an event that is no longer active. Putting a value that varies within `standard` on the event narrows ADR 0018's placement rule — see Consequences.
- **On the event for walk-up, in `AdminSettings` for standard (rejected).** Leaves standard events untouched. But one value then has two homes chosen by kind, and every site that copies a race's distance has to pick the right one — the split ADR 0018 cites `includeAllRaceData` for, which lives in two places and has only one copy ever read.
- **On the event, fixed for every kind (rejected).** One rule and no new capability. But standard events have a documented requirement to adjust the distance mid-event (`product-requirements.md:93`), and at a standard event a new event also means every racer registers again.

**Which races a standard event's change reaches**

- **`scheduled` and `staging` only (chosen).** The same window as the `lane swap` (`canSwapRaceLanes`, `race-lanes.ts:63`): a change reaches a race in `scheduled` or `staging`, and never one in `countdown`, `active` or `interrupted` — including a race the app marked `interrupted` at startup while it was still only staged (`Database.ts:170`, `:596`). To give a counting-down race the new distance, the host resets it to staged first.
- **`scheduled`, `staging` and `countdown` (rejected).** The smallest fix for the defect below, but it still lets the projector's distance header change in front of the crowd during the countdown.
- **Today's rule, with the defect filed separately (rejected).** Moving the distance onto the event rewrites the code that applies a change anyway, so the fix would be written twice.

**Where the operator enters it**

- **A create-event form of its own (chosen).** Name, kind and distance, replacing today's yes/no confirm, whose warning moves into the form. Creation has to grow a kind picker under ADR 0018 regardless.
- **Fields added to the existing confirm (rejected).** The smallest change, but it turns a destructive yes/no into a form, and still takes the new event's name from the field that edits the current event (`event-tab.tsx:284`).

**What the form suggests**

- **The current event's distance (chosen).** An operator's distance carries from one event to the next, as the global setting does today, without a second stored copy. The event the app creates for itself when none exists (`Database.ts:528`) has no form and uses the built-in 250 m.
- **Always 250 m (rejected).** A walk-up event never quietly inherits a league night's distance, at the cost of retyping it every time the operator wants something else.
- **A suggestion per kind (rejected).** Needs a new, non-boolean kind of manifest entry — capabilities are booleans (ADR 0022) — to hold a number nobody has ridden at a stall yet.

## Consequences

- **A defect in every event kind closes with this.** `applyRaceDistanceSetting` (`app.ts:1843`) rewrites the current race unless it is `active`, and the current race can be in `countdown` or `interrupted` (`Database.ts:162`). An `interrupted` race resumes from its banked metrics but reads the rewritten distance (`active-race.ts:46`, `:60`), so a rider stopped at 140 m of a 250 m race, with the distance then changed to 100 m, is finalized with 140 m against a 100 m race distance — a run ADR 0022's rule would rank, with a time that also counts the downtime, since the clock runs from the race's original start (`active-race.ts:57`). ADR 0022's claim that such riders "fail the distance test unaided" did not account for this case. The `scheduled`/`staging` window makes it unreachable. `product-requirements.md:93` is amended to the new window and marked `Partial`.
- **The server enforces the lock; the hidden editor is presentation.** `hasAdjustableRaceDistance` gates the Event tab's editor through `requires` like any other surface (ADR 0021), and the event update path refuses a distance change when the active event's capabilities say it is fixed. The board's guarantee rests on that refusal, not on a control being absent.
- **A walk-up event shows its distance as a plain value, with no trace of the editor.** No disabled input and no "fixed for this event" note on the Event tab, per ADR 0021. The one place the permanence is stated is the create-event form, when walk-up is picked, because that is the only moment the operator can still act on it. That line is not a breach of ADR 0021's no-trace rule, which governs the admin window of an event whose kind already withholds a capability: at creation the kind is still being chosen, and the line follows the selected kind's `hasAdjustableRaceDistance` rather than a hand-kept list of what the kind switches off — the drift ADR 0021 rejected its one-line summary for.
- **Test rides happen before the evening's event is created, never inside it.** A distance tried at setup is tried in a throwaway event, and the real one is created with the number that felt right. The ticket also asked what distance suits a market; this ADR records none. It is a venue decision, like the display hardware, and the create-event form is where the operator makes it.
- **A mid-evening restart costs the riders entered before it, and that is accepted.** The desk's find-or-create matches against tonight's riders (ADR 0020), and the snapshot carries only the active event's racers (`snapshot-assembler.ts:215`), so a rider from before a restart is created again, and one evening's leads land in two events. Restarts are expected to be rare, and a duplicate is the kind of record a `racer merge` (ADR 0008) folds back in — once that tool is built, which it is not yet. Nothing carries riders across events.
- **ADR 0022's rule is unchanged, and its open consequence closes.** "Raced at the locked walk-up distance" now reads "raced at the event's race distance", which holds by construction at a walk-up event.
- **This contradicts ADR 0018's placement rule as written, and narrows it rather than overturning it.** ADR 0018 says anything an operator varies within a kind belongs in `AdminSettings`, and the race distance varies within `standard` yet moves onto the event. The narrowing is ADR 0022's test for placing an operator dial: a dial that varies with the venue's screen (the board's row count, the ticker speed) is an `AdminSettings` field, and a value every run in the session is measured against belongs to the session's event — even when, like the distance, the operator picks it with the venue in mind.
- **`AdminSettings.targetDistanceMeters` is retired, not kept as a default.** A migration adds the distance to `events`, back-fills every existing event from the current setting (250 m if unset), and the setting and its validation (`validation.ts:171`) go, so nothing about a current install changes except where the value lives. The `Race Distance` panel moves to the Event tab, as ADR 0021 already placed it, and edits the active event.
- **The user guide's distance step changes when this ships.** Step 3 of `docs/user-guide/03-running-an-event.md` points at the Race Desk and says a change "won't alter a race that's already staged" (`:84`) — wrong today, and still wrong under this decision, where a staged race picks the change up.
- **No production code ships with this decision.** Like ADRs 0020–0022, it waits on ADR 0018's `kind` column and capability manifest.
