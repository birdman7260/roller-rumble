# RaceCountdown owns the countdown as in-memory state; the countdown start is not persisted

**Status:** accepted — amends [ADR 0010](./0010-os2l-cue-owns-countdown.md) (the app owns the visible countdown) and extends the leaf-module discipline of [ADR 0003](./0003-finalization-cascade-coordination.md)

The countdown mechanics that ADR 0010 gave the app — the visible countdown timer, the `pre-roll` that delays the box's `g`, and the music-locked `GO` — were smeared across `RollerRumbleApp` as five raw timer/flag fields woven through six methods, reachable in tests only by reflecting private methods off the prototype. We extract them into a **`RaceCountdown`** module (the temporal sibling of `ActiveRace`, owning a race from its start trigger through `GO`) with a small interface: `start`, `abort`, `dispose`, and a `getTiming` read. The module owns countdown mechanics only — timers, the pre-roll math `max(0, N − BOX_COUNTDOWN_MS)`, and box arming. The coordinator keeps everything cross-domain: the persisted `state="countdown"` flip, the start guards, the OS2L **trigger** arming (which governs _entry_ into a countdown, distinct from the box arming _inside_ one), and — following ADR 0003's "leaf never emits" rule — activation and snapshot emission, reached through injected `onGo`/`onTick` callbacks rather than the module acting itself.

The load-bearing decision: **the countdown's timing — its start instant and duration — lives only in memory, inside `RaceCountdown`, and is surfaced to the `AppSnapshot` through `SnapshotContext`** (exactly as the duration already was), rather than on the race row. The `races.countdown_started_at` column is therefore **de-persisted** — it goes dormant, no longer written. We found the column had exactly one reader, the `SnapshotAssembler` computing the projector's remaining-seconds clock (ADR 0002 keeps that a pure read); nothing ever resumed a countdown from it. Persisting a countdown-in-flight would only matter for crash recovery, and a countdown is the one race phase where dropping it on restart is correct — there is nothing to resume, the operator simply re-triggers. Recovery of a race that crashed while **active** is a separate concern already served by the `interrupted` flow (restart / resume / finalize on the persisted metrics), which this does not touch.

## Consequences

- A whole bug class disappears: with no persisted countdown timestamp, the "timers torn down but `countdownStartedAt` left stale" hazard that made `abort` intricate cannot occur. `abort` becomes one idempotent teardown, a no-op when idle.
- `SnapshotContext` swaps its `countdownDurationMsFor(raceId)` lookup for the module's `getTiming()`, and the assembler stops reading `currentRace.countdownStartedAt` while still gating on the persisted `state="countdown"`. A golden-snapshot test guards that the projector clock renders byte-identically after the move (ADR 0002).
- `races.countdown_started_at` stays in the schema as a dormant column — migrations never edit existing files after data exists, and dropping it earns nothing. A future reader should expect it unread, not resurrect it.
- Timing behaviour is tested by constructing `new RaceCountdown(...)` directly with a fake arming port and `vi.useFakeTimers()` (the `ActiveRace` precedent — global timers, no injected clock), so the countdown's test surface is its real interface rather than reflected private methods.
