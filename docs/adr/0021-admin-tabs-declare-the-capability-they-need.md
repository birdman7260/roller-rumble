# The admin tab rail survives, filtered by each tab declaring the capability it needs

**Status:** accepted — resolves [issue #42](https://github.com/birdman7260/roller-rumble/issues/42) on the [walk-up event map (#30)](https://github.com/birdman7260/roller-rumble/issues/30). Builds on [ADR 0018](0018-event-kind-and-derived-capabilities.md) (`event kind`, `event capability`) and [ADR 0020](0020-walk-up-desk-seats-riders-on-bikes.md) (`walk-up desk`).

ADR 0020 fixed what the host operates and left where it lives to this ticket. A `walk-up event` switches off tournaments, payments, Web Push, the tunnel and the racer page, which guts three of the Race Desk's four panels (`Racer Queue Signups`, `Add To Queue`, `Queue` — `race-tab.tsx:60,145,221`), kills the Tournaments tab outright, empties the `Tunnel` and `Notifications` panels plus four toggles in the Settings tab's own general panel (`settings-tab.tsx:131`, confusingly titled just "Settings"), and empties the `Event Payments` panel on the Event tab (`event-tab.tsx:143`). Five tabs and a static array (`adminTabs`, `types.ts:3`) have to answer for that.

We decided the **tab rail survives, filtered**. Each entry in `adminTabs` declares the `event capability` it needs — `requires?: EventCapabilityKey` — and `AdminTabRail` renders the entries whose requirement the active event's capabilities satisfy. The `walk-up desk` is **its own tab id**, not a re-skin of the Race Desk's slot. Nothing else is added: the registry's existing order does the remaining work, because **the operator lands on the first visible tab**.

```
walk-up-desk   requires hostComposesRaces   ┐ standard: Event · Race Desk · Racers ·
event          —                            │           Tournaments · Settings
race           requires hasQueue            │           → lands on Event (unchanged)
racers         —                            │
tournaments    requires hasTournaments      │ walk-up:  Walk-Up Desk · Event · Racers ·
settings       —                            ┘           Settings → lands on the desk
```

`requires` names a capability that must be **true**; there is deliberately no "requires-not". Both surfaces that disappear express themselves as a capability someone else _has_ — the Race Desk is the `Queue`'s surface (`hasQueue`), the desk is the host-composition surface (`hostComposesRaces`) — which keeps the filter a one-liner and forces the next gated tab to name a real capability rather than a negation.

The load-bearing consequence: **`AdminTabId` is a flat union containing ids that are invalid for the current event**, so a runtime clamp, not the type system, is what keeps `activeTab` legal.

## Considered Options

**Where the `walk-up desk` sits among the tabs**

- **Its own tab id (chosen).** `walk-up-desk` is a distinct entry with a distinct label and description, sitting alongside a `race` entry that a walk-up event never shows. The rail then says what it means: the glossary already reserves "Race Desk" for the queued-event tab, and a slot whose name and contents both change by kind is a slot pretending to be one thing. It also lets the desk lead the walk-up rail while `event` keeps leading the standard one, from a single ordered registry. Its cost is the flat union — see the clamp, below — and that cost is smaller than it looks: the admin surface has exactly one hard-coded `setActiveTab` literal (`race-tray.tsx:132`, `"tournaments"`), and it is already unreachable at a walk-up event because it is guarded on an `activeTournament`.
- **Reusing the `race` slot (rejected).** One id, so the union stays honest for every kind and no `setActiveTab` call site can name a tab that is not there. Rejected because it buys that safety by making `race` mean two unrelated surfaces with two labels and two descriptions, which is the ambiguity ADR 0018 spent a whole enum avoiding — and it would make "which surface is the `race` tab" a question you answer by reading the capability manifest rather than the rail.
- **No rail at all — the desk is the admin window (rejected).** The map licenses a restructure, and maximum focus on the loop is defensible for an operator whose only job is the loop. Rejected because the operator genuinely leaves the desk during an evening — Racers to fix a name or add a phone number ([#39](https://github.com/birdman7260/roller-rumble/issues/39)), Settings when something is wrong — so the other three tabs still have to be reachable, and reaching them behind a collapsed menu is a second navigation mechanism used by exactly one `event kind`.

**How a tab's visibility is expressed**

- **On the tab entry (chosen).** `adminTabs` stays the one registry, and a new tab opts into a capability where it is defined rather than in a file the author may not think to open. It also keeps `packages/shared` free of a renderer-only vocabulary: the same manifest is read by the projector and the racer surface, and admin tab ids mean nothing to either. This is the `CompetitionPresetDefinition` shape already in `packages/shared` — the definition declares what it needs, the consumer asks.
- **The kind manifest carrying the tab list (rejected).** The manifest would be the single declarative picture of a kind, which is genuinely attractive while there are two kinds. Rejected because adding a tab then means editing two places, one of which must be edited once per kind, and a forgotten row is silent — the tab simply never appears for that kind, with no type error. ADR 0018's guarantee runs the other way: adding a _capability_ forces every kind to answer. Declaring on the tab inherits that guarantee; listing tabs per kind does not.

**Switched-off subsystems in Settings**

- **Hidden, with no explanation (chosen).** Tunnel, Notifications, `Event Payments`, and the four queue/racer-page toggles in the general panel (`allowAccountlessRacerSignup`, `showPublicRacerInfoWithoutLogin`, `maxActiveQueueEntriesPerRacer`, `autoStageNextRace`) simply are not rendered. The operator this is built for is a dedicated one who set the event up; a Settings tab holding only things that do something is worth more to them all evening than a reassurance they need once.
- **Present-but-disabled with a reason (rejected).** Nothing goes missing, and the operator never wonders whether the build is broken. Rejected because a disabled control implies it could be enabled, and under ADR 0018 the `kind` is immutable — the only way to turn the tunnel back on is to create a different event, which is not what a greyed-out toggle communicates. It also leaves the walk-up Settings tab mostly composed of things that do nothing, which is the opposite of what a stripped-down kind is for.
- **Hidden, plus one line naming what the kind switched off (rejected).** The cheap middle: answer "is it broken?" once, in one place, without a field of dead controls. Rejected as meta-commentary that ages badly — it is a second list of capabilities, maintained by hand, that drifts from the manifest the moment a capability is added.

## Consequences

- **`activeTab` must be clamped to the visible set, not just defaulted.** `activeTab` is in-memory reducer state (`admin-page.tsx:49`) and is not persisted, so no restart can strand it — but switching the active event can, within a session, since a different event may have a different `event kind`. When the visible set changes and no longer contains `activeTab`, it falls back to the first visible entry. This is the price of the flat union and the only place that price is paid.
- **The landing tab is derived, not configured.** First visible entry, which is `event` for a `standard` event — today's default, unchanged — and the `walk-up desk` for a `walk-up event`, whose operator should not open the app on a details page. Nothing stores a preferred tab and nothing branches on the kind to pick one. The cost is that registry order is now load-bearing: inserting a capability-gated tab at the head of the array moves where that kind's operator lands.
- **A capability the kind withholds leaves no trace in the admin window.** This is one rule, not a Settings rule — it covers the hidden panels, the hidden tabs, and `subsystem health`, which omits a subsystem the kind switched off rather than reporting it degraded. A walk-up event's status surface must never show a failed tunnel or unconfigured Web Push, because "off by design" and "broken" render identically once something reports amber. The map's _no-network field readiness_ item stays separate and still open: it is about subsystems the kind keeps but the venue breaks, which is a real failure the operator does need told.
- **The race tray needs no rework, which is the opposite of what #42 assumed.** Its show-condition (`race-tray.tsx:72`) is `resultPresentation ?? currentRace ?? activeTournament ?? nextQueueEntry`, and the ticket read the two dead terms as a reason to rewrite it. They are not: `activeTournament` and `nextQueueEntry` are null _by construction_ at a walk-up event, so the expression already degrades to `resultPresentation ?? currentRace` on its own. The same is true throughout the component — the tournament and queue branches of the meta block are unreachable, `showOpenTimeTrialStageAction` is false because it requires a `nextQueueEntry` (`:77`), and the one hard-coded `setActiveTab("tournaments")` (`:132`) is guarded on an `activeTournament`. The tray is shared with `standard` events and must not be edited for this: what survives is exactly the live-race and result controls, which is what a walk-up host wants from Event, Racers or Settings anyway. A capability-gated surface can be correct by construction, and this one already is.
- **Event, Racers and Settings survive and are thinned by the same rule.** Event keeps its details and `Session Snapshot` and shows the `event kind` read-only per ADR 0018, losing `Event Payments`; its `signup prompt` copy fields configure a card the projector no longer shows, and what replaces them is [#37](https://github.com/birdman7260/roller-rumble/issues/37)'s question, not settled here. Racers keeps the roster but is no longer how someone gets racing — the desk's find-or-create is — which frees the tab for whatever [#39](https://github.com/birdman7260/roller-rumble/issues/39) and [#40](https://github.com/birdman7260/roller-rumble/issues/40) decide it should carry; neither is pre-empted here, and in particular this ADR does not say Racers is where contact details get captured. Its `attach QR` needs a racer page to sign into, so it goes with the rest.
- **Race Desk is removed, not transformed, and `Race Distance` moves to the Event tab.** Gating the tab on `hasQueue` is the honest reading: three of its four panels are the `Queue`. The fourth, `Race Distance` (`race-tab.tsx:114`), is the one thing that would have justified keeping a queue surface with its queue removed, so this ADR places it rather than leaving it homeless — it belongs on the Event tab, with the other event-scoped facts the kind fixes, not on the `walk-up desk`, which is for composing a race and not for configuring the event. Whether that control is locked, and what happens if the host changes it mid-event, stays [#38](https://github.com/birdman7260/roller-rumble/issues/38)'s to decide; this ADR only says which tab it is on.
- **Tournaments is the only tab that needed no argument.** `requires: "hasTournaments"`, already false from ADR 0018's manifest.
- **This is the pattern every later surface copies.** The next thing the app hides from a kind — a projector card, a racer-page section, a settings field — declares the capability it needs at its own definition site and is filtered by its container. No new mechanism, and nothing anywhere compares against `"walk-up"`.
- **No production code ships with this decision.** As with ADR 0020, the rail cannot be filtered until ADR 0018's `kind` column and capability manifest exist, which are still an ADR only.
