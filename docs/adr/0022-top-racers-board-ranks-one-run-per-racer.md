# The top racers board ranks one best qualifying run per racer, derived in the snapshot assembler

**Status:** accepted — resolves [issue #34](https://github.com/birdman7260/roller-rumble/issues/34) on the [walk-up event map (#30)](https://github.com/birdman7260/roller-rumble/issues/30). Builds on [ADR 0018](0018-event-kind-and-derived-capabilities.md) (`event kind`, `event capability`), [ADR 0021](0021-admin-tabs-declare-the-capability-they-need.md) (`requires` names a capability that must be true), [ADR 0011](0011-finish-budget-defers-finalization.md) (`finish budget`) and [ADR 0002](0002-snapshot-assembler-boundary.md) (the assembler is a pure read). **Revises ADR 0018** on one point: its sketched `idleProjector` capability becomes the boolean `hasTopRacersBoard` — see _Which capability grants the board_ below. **Revised by [ADR 0025](0025-standard-event-idle-projector-shows-the-top-racers-board.md):** a `standard` event shows the board too, so `topRacers` is always derived and is never `null` yet.

The map locks the metric — fastest time over the locked walk-up distance, current event only — and leaves every rule around it open. The obvious hook is already there and is wrong for the job: `RacerStats.bestFinishTimeMs` (`types.ts:527`) is per-racer and is already a minimum finish time, but it is computed as `min(finishTimeMs)` over results scoped only by `includeAllRaceData` (`snapshot-assembler.ts:230`, `:59`) — no distance filter at all, and with that toggle on it silently ranks other events' runs. It is a career stat wearing the board's shape.

A row on the **`top racers board`** is **one racer's best qualifying run**. A run qualifies when it belongs to the active event, its race was run at the locked walk-up distance, and the rider actually crossed the line. Solo and head-to-head runs rank together with nothing distinguishing them. Ties order by the earlier run. The board is derived in `SnapshotAssembler`, sliced to an operator-set row count, and a racer with no qualifying run is simply absent.

**Best-per-racer is what the board is _for_.** The map keeps the board current-event-only so "a newcomer at 9pm still has a real shot at the top spot"; one rider holding three of five rows defeats that at 6pm instead, and the rider it rewards is the stall regular rather than the stranger the board exists to recruit.

**A non-finish is detected by distance, not by a missing time.** The ticket asked what a rider "with no finish time" contributes; no such row exists. The only writer of results is `ActiveRace.finalize` (`active-race.ts:270`), which stores `finishTimeMs: metric.finishedAtMs ?? metric.elapsedMs` (`:277`), so a rider force-finished when their `finish budget` expires carries a real, plausible-looking number for a partial distance. A board that tested for null would rank someone who covered 140m of a 250m race. The test is `result.distanceMeters >= race.targetDistanceMeters`, the same comparison the crossing test makes at `active-race.ts:170`. An `interrupted` or `cancelled` race needs no rule of its own either. A race sitting in `interrupted` has written no results yet, and `restartInterruptedRace` (`app.ts:2612`) discards its telemetry outright; the one path that does produce results from it, `finalizeInterruptedRace` (`app.ts:2645`), resumes the race purely to run that same force-finish path — so its riders land short of the line and fail the distance test unaided. A `cancelled` race never writes results at all.

**The sort must be a total order**, because the board re-derives on every snapshot broadcast: `finishTimeMs` ascending, then the result's `createdAt` ascending, then `racerId`. The middle term is the tiebreak that was actually asked for — the earlier run holds the higher slot. The last term is not decoration: without it two rows tied on both time and timestamp (two riders in one race, written in a single `createResults` batch) have no defined order and can swap places between broadcasts, which on a projector reads as the board twitching.

The shape:

```
raceProjection.topRacers: TopRacersEntry[] | null
TopRacersEntry = { racerId, raceId, finishTimeMs }
```

Ordered fastest first and already sliced, so the array index _is_ the rank and no rank field ships. `null` means this `event kind` has no board; `[]` means the board is empty, which is the 5pm state [#37](https://github.com/birdman7260/roller-rumble/issues/37) has to design. Names and avatars are not carried — `snapshot.racers` already holds every racer in the event — so the board carries ranking and nothing else. `raceId` is carried because [#41](https://github.com/birdman7260/roller-rumble/issues/41) wants to mark a newly-placed row, and that is not answerable from the rider alone: a returning rider's best run may not be the run that just finished.

The row count is an operator setting, `AdminSettings.raceDisplayTopRacersRows` (default 5, bounded 3–10), and the assembler slices to it. Making the board's type scale respond to that value is [#37](https://github.com/birdman7260/roller-rumble/issues/37)'s.

## Considered Options

**Where the board is derived**

- **In `SnapshotAssembler` (chosen).** It is the only place that can. The distance filter needs `races.targetDistanceMeters` (`schema.ts:253`) — the race's target, snapshotted per race at creation — and `results` carries only `distanceMeters`, the distance a rider actually covered (`schema.ts:281`). So the board is a join, and the assembler is the one component holding both tables. It also matches ADR 0002: this is a pure read that adds a derived field, which is exactly the assembler's job.
- **Computed on the projector (rejected).** Tempting because `RacerStats` is already per-racer and already on the wire. But the projector cannot do it: `AppSnapshot` carries no results array at all, and the only races on it are the current one and whichever race the `resultPresentation` is showing (`types.ts:539`) — so there is nothing to rank and no target distance to rank it against. Making it possible would mean broadcasting the event's entire result and race history on every snapshot, to every surface, to render five rows.
- **Reusing `bestFinishTimeMs` in place, fixed (rejected).** The cheapest-looking option — add the distance filter and force event scope, and the board falls out of the existing field. Rejected because it is not the same question: `bestFinishTimeMs` feeds the racer page's "Best Finish" stat (`racer-sections/stats.tsx:42`), where a racer's personal best across every event and distance is the _correct_ answer. Narrowing it to serve the board would quietly break a stat on another surface, and widening the board to match it is what this ADR just rejected.
- **A materialized board table (rejected).** Precomputed on finalize, so the assembler reads a handful of rows. Rejected as a cache with real invalidation surface — every finalize, every `racer merge` (which reparents results), every `deleteResultsForRace` (`Database.ts:1583`), and every change to the row-count setting or the locked distance — bought for a derivation over the dozens of results one evening at a stall produces.

**What a row is**

- **Best qualifying run per racer (chosen).** One row per racer, as argued above. It also matches the shape already on the wire: `racers` is one entry per racer, so a board keyed the same way needs no new identity plumbing.
- **Every qualifying run (rejected).** A busier board that rewards persistence, and persistence is a real thing to reward at a stall where the same people come back between beers. Rejected because it inverts the recruiting purpose: the strongest rider takes as many slots as they have runs, and the board stops being evidence a passer-by could be on it.

**How a non-finish is detected**

- **Distance covered against the race's target (chosen).** The exact mirror of the test that decides a rider crossed the line, so the board and the race agree on what finishing means by construction.
- **A null `finishTimeMs` (rejected).** What the ticket assumed, and what the type invites — `finishTimeMs?: number | null` (`types.ts:279`). It is never null on the only path that writes results, so this rule would silently admit every force-finished partial-distance rider.
- **`placement` (rejected).** Also already there, and also says nothing about finishing: a solo rider is always placement 1 whether or not they reached the line, and a force-finished trailing racer is placement 2 by design (ADR 0011).

**Solo versus head-to-head**

- **One board, unmarked (chosen).** Same distance, same effort; a rider being chased does go faster, but at walk-up scale that difference is small against the spread between strangers in jeans, and per [#41](https://github.com/birdman7260/roller-rumble/issues/41) solo is the common case, not the edge case. Accepted knowingly: the board's claim is "fastest time here tonight", not "fairest comparison".
- **One board, head-to-head marked (rejected).** Honest about the asymmetry, at the cost of a column that has to survive being read from across a street at dusk by someone giving it two seconds — the one thing the board's legibility budget cannot spare.
- **Solo runs excluded (rejected).** Strictly comparable, and it would empty the board: a walk-up event runs solo constantly, so most of the evening's times would never rank.

**Which capability grants the board**

- **A boolean `hasTopRacersBoard` (chosen).** ADR 0018 sketched this capability as `idleProjector`, "what the projector shows while idle" — a capability with a value rather than a truth. ADR 0021 then fixed `requires` as naming a capability that must be _true_, and the board needs exactly that gate, both for its Settings field and for whatever [#37](https://github.com/birdman7260/roller-rumble/issues/37) builds. A boolean also turns out to be sufficient: the `signup prompt` recruits into a queue via a QR, so it is already conditioned on `hasRacerPage`, and the idle projector's two states fall out of two booleans that each mean something on their own.
- **Keeping `idleProjector` as an enum (rejected).** One capability instead of two, and a third idle state later is one more enum member rather than a third boolean plus a rule about which wins. Rejected because it is the only value-valued capability in the manifest, so it cannot use `requires` and forces a second filtering vocabulary for the sake of a third state nobody has asked for.

**How many rows**

- **An operator setting (chosen).** The map's own standing risk is that the display hardware is unresolved — an outdoor projector at 7pm in July may be unreadable, and the answer may end up being an LED panel or a TV. The right row count is a property of the screen that is finally standing at the stall, which is not knowable now and may differ between evenings. It lands in `AdminSettings` beside `raceDisplayTickerSpeed` (`validation.ts:169`, slider at `settings-tab.tsx:302`), its direct precedent as a projector-legibility dial, and _not_ on the event row: ADR 0018's rule is that what an operator varies within a kind is a setting, and this varies with the venue's screen rather than with the session's data.
- **A fixed constant (rejected).** One number, no control, nothing for an operator to get wrong, and [#37](https://github.com/birdman7260/roller-rumble/issues/37) designs against a known shape. Rejected for the same reason: the number depends on hardware nobody has picked, so a constant would be a guess frozen into `packages/shared`.
- **Fit to the available height (rejected).** The most automatic answer, and the one that always fills the screen. Rejected because it cannot be reconciled with deriving the board server-side: the assembler has no viewport, so either the payload size depends on a measurement it cannot see, or the slice moves to the projector and the board's cap stops being part of the contract. It also leaves the operator no way to overrule a result they can see is wrong from where the crowd stands.

## Consequences

- **The board's central filter depends on a lock that does not exist yet, and this sharpens [#38](https://github.com/birdman7260/roller-rumble/issues/38) rather than settling it.** Each race snapshots the settings distance onto its own row at creation (`app.ts:2345` for a queued race, `:2678` for a tournament race), so the filter is always computable; what is undecided is what the operator may do to the setting mid-event. Under this rule the failure mode is specific and severe: change the distance after ten runs and the board empties, because every recorded run now fails the match. That is #38's to answer — hard-lock, warn, or group by distance — and it now has a concrete consequence to answer against instead of "the board handles it".
- **`bestFinishTimeMs` is left exactly as it is.** It stays the racer page's career stat, wrong for the board and right for its own surface. Nothing in this ADR touches `buildRacerSummaries`.
- **The distance test ships as one shared predicate, not two copies of the same comparison.** The board's qualifying rule and `ActiveRace`'s crossing test are the same question — did this rider reach the line — and the board's correctness rests on them staying identical. Written out twice they agree only by inspection, and the next change to how crossing is judged (a tolerance for float accumulation, a rounding rule) would desynchronize the board from the race silently, in the direction that puts unearned times on a public screen. Whoever implements this puts the comparison in one place and calls it from both.
- **The assembler gains one query, and only for events that have a board.** Deriving the board needs the event's races indexed by id to reach each result's target distance, which `assemble` does not read today (it calls `getCurrentRace`, not `listRaces`). Gating the derivation on `hasTopRacersBoard` means a `standard` event pays nothing and gets `topRacers: null`, which matters because that query is a full per-event race scan on every snapshot broadcast — cheap at a stall's dozens of races, not something to hand a league night with hundreds.
- **The board is public by construction, so `forSurface` needs no rule for it.** Names and times on a projector facing a street are the least private thing the app holds. It passes through to the racer payload unstripped, which is moot at a walk-up event — there is no racer page — and harmless anywhere else.
- **Ties are ordered but never announced.** Two rows an operator can see are tied at tenths (`race-results-overlay.tsx:23` formats to one decimal) simply sit in their order, and the board says nothing about it. Exact millisecond ties are the rarity; apparent ties are routine, and a shared-rank marker would be ink spent on the common case's cosmetics.
- **A racer with no qualifying run leaves no trace.** No unranked section, no DNF list, no "rode but did not place" line — the same rule ADR 0021 set for capabilities a kind withholds, applied to a rider the board has nothing to say about. Their run still happened, is still in `results`, and still exports with the leads.
- **`raceDisplayTopRacersRows` is the first `AdminSettings` field gated by an `event capability`.** ADR 0021 established the mechanism for tabs and predicted the next surface would copy it; this is that surface, and the copy is exact — the field declares `requires: "hasTopRacersBoard"` at its definition site and its container filters it, so it is absent rather than disabled at a `standard` event. Bounded 3–10 because below three the board is a podium and above ten the type has shrunk past the legibility the whole feature exists for. The bound is the real handoff to [#37](https://github.com/birdman7260/roller-rumble/issues/37): its layout has to stay legible across the whole range rather than at one chosen count, and if some part of that range cannot be made to work, narrowing the bound is #37's call to make — this ADR fixes that the count is operator-set, not what its limits finally are.
- **No production code ships with this decision.** As with ADR 0020 and ADR 0021, the board cannot be derived until ADR 0018's `kind` column and capability manifest exist, and its distance filter additionally waits on [#38](https://github.com/birdman7260/roller-rumble/issues/38). What ships is the contract [#37](https://github.com/birdman7260/roller-rumble/issues/37) needs to design a layout against: one row per racer, no DNFs, no shared ranks, an operator-set row count, and an empty state distinguishable from no board at all.
